什么是即时通讯

学习：https://mp.weixin.qq.com/s/o8nMh4fJd2zsOq0zOHZAag

真正的 IM 系统，解决的不是“能不能发出去”，而是下面这一整组问题：

  • 对方在线时，消息如何实时送达？
  • 对方不在线时，消息如何不丢？
  • 用户再次上线，消息如何不重、不漏、不乱？
  • 群聊里，上千人同时在线或离线，消息怎么保证一致性？

要理解这些问题，我们必须先从 IM 中最核心的对象——消息 讲起。

一、在线消息与离线消息

IM 的第一道分水岭

在 IM 领域，消息是否“在线送达”，会直接决定整个系统的架构复杂度。

1. 在线消息（Online Message）

当客户端处于在线状态，服务端通过已有连接，将消息实时送达客户端。

这类消息的典型特征是：

  • 低延迟（通常是毫秒级）
  • 依赖 长连接
  • 大多数情况下，通过消息直推完成

2. 离线消息（Offline Message）

现实世界里，用户不可能 24 小时在线。当客户端不在线时，消息并不会“凭空消失”，而是会：由服务端暂存，等客户端重新上线后，再分批补发。这部分消息，就叫做 离线消息。

离线消息的存在，意味着 IM 系统必须具备：

  • 存储能力
  • 消息补齐能力
  • 客户端与服务端的状态协同能力

二、消息直推 vs 通知拉取

两种不同的设计哲学

很多人以为：“IM 就是服务端把消息推给客户端。” 但在真实系统中，其实存在两种模式。

1. 消息直推（Push Message）

消息直推指的是：服务端通过与客户端的长连接，直接把完整消息推送到客户端。

优点很明显：

  • 延迟低
  • 实时性强
  • 客户端逻辑简单

但缺点同样明显：

  • 对长连接稳定性要求极高
  • 弱网、切后台、网络抖动都会影响成功率

2. 通知拉取（Notify & Pull）

  • 服务端只推送一个**“有新消息”的通知**
  • 客户端根据自己本地的消息偏移量，主动从服务端拉取增量消息

这种模式通常会配合一个非常重要的概念使用：收件箱。

三、收件箱

服务端视角下的“离线缓存”

收件箱（Inbox），也叫信箱，是 IM 系统中一个极其关键、但又容易被忽略的结构。

可以把它理解为：服务端为每个用户维护的“离线消息缓存区”

当用户离线时：

  • 新消息会被写入该用户的收件箱
  • 不会立即投递给客户端

当用户上线时：

  • 客户端根据本地进度
  • 从收件箱中增量同步消息

这正是“通知拉取”能够成立的基础。

四、会话列表

你打开 IM 后看到的“第一屏”，无论是微信、QQ 还是 Slack，进入 IM 后看到的第一屏，几乎都是：会话列表（sessionList / chatList）

它并不是简单的 UI，而是一个高度浓缩的状态集合，通常包含：

  • 会话最后一条消息
  • 未读消息数
  • 置顶状态
  • 免打扰状态

而这些信息的计算，离不开两个非常重要的索引概念。

五、消息 Seq 与 ReadIndex

IM 中的“秩序感”

1. 消息 Seq（Sequence）：在同一个会话内，单调递增的消息序号。

它的核心作用是：

  • 帮助客户端判断是否丢消息
  • 快速发现“断档”，并触发补拉

没有 Seq，客户端只能“猜”。

2. 消息 ReadIndex（已读索引）：用户维度的“已读位置标记”，只对接收方向的消息生效。

它的特点是：

  • 千人千面（同一会话，不同用户不同值）
  • 用于快速计算未读数
  • 是会话列表未读红点的基础

六、历史消息与定向消息

规模化后的复杂性

当消息发送成功，它就会成为历史消息，并需要被长期存储。

在群聊中，为了节省空间：

  • 群消息只在群维度保存一份
  • 用户通过索引关联

而更进一步，还有一种更复杂的形态：定向消息，在群场景中，只投递给部分成员的消息。

这类消息会直接挑战：存储模型、投递模型、权限与可见性设计

一、Go语言简介

Go语言出自Ken Thompson、Rob Pike和Robert Griesemer之手，起源于2007年，并在2009年正式对外发布，其实都是Google的，设计Go语言的初衷都是为了满足Google的需求。

Go的主要目标是“兼具Python等动态语言的开发速度和C/C++等编译型语言的性能与安全性”，旨在不损失应用程序性能的情况下降低代码的复杂性，具有“部署简单、并发性好、语言设计良好、执行性能好”等优势。

最主要还是为了并发而生，并发是基于goroutine的，goroutine类似于线程，但并非线程，可以将goroutine理解为一种虚拟线程。Go语言运行时会参与调度goroutine，并将goroutine合理地分配到每个CPU中，最大限度地使用CPU性能。

Go语言（又称为Golang）是一种开源的编程语言，由Google开发并于2009年首次亮相。它是一种静态类型、编译型的语言，拥有自动垃圾回收机制和强大的并发编程支持。

Go语言被设计成简洁、易于学习和使用，同时具备高效、可靠和可扩展的特性。它的语法风格类似于C语言，但是去掉了许多C语言中的复杂特性，如指针和内存管理。

Go语言可以用于编写各种类型的应用程序，包括服务器端应用程序、网络应用程序、云平台应用程序、操作系统和系统工具等。它也被广泛用于大型互联网公司和其他组织的内部开发中，例如Google、Uber、Dropbox和Docker等。

三、工程结构

在设置GOPATH环境变量的时候，这个目录里面又分了三个子目录bin、pkg、src，分别用于存放可执行文件、包文件和源码文件。当我们执行Go命令的时候，如果我们指定的不是当前目录的文件或者绝对路径的目录的话，就会去GOPATH目录的去找。这样在GOPATH目录创建了xxx的目录后，就可以在任意地方执行 go build xx 命令来构建或者运行了。

pkg目录应该是在执行 go install 后生成的包文件，包括.a这样的文件，相当于一个归档。

这样对于我们具体项目来说并不好，没有Workspace的概念来隔离每个项目了，所以我觉得这个GOPATH目录放的应该是公用的项目，例如开源依赖的。我们在开发过程中，也会下载很多的依赖，这些依赖都下载到这个目录，和我们的项目文件混在一起了。

另外，通过IDE可以设置project的GOPATH，相当于在执行的时候给GOPATH增加了一个目录变量，也就是说，我们创建一个项目，然后里面也有bin、src、pkg这三个目录，和GOPATH一样的，本质上，IDE在运行的时候其实就是设置了一下GOPATH。

Go语言在寻找变量、函数、类属性及方法的时候，会先查看GOPATH这个系统环境变量，然后根据该变量配置的路径列表依次去对应路径下的src目录下根据包名查找对应的目录，如果对应目录存在，则再到该目录下查找对应的变量、函数、类属性和方法。

官方提供了Go Modules的方法更好解决。

Go Modules

Go Modules 是 Go 语言官方提供的依赖管理机制，自 Go 1.11（2018年）引入，并在 Go 1.16（2021年）起成为默认且推荐的依赖管理方式。它彻底解决了早期 Go 开发中长期存在的“GOPATH 依赖地狱”问题，使 Go 项目可以脱离 GOPATH、精确控制依赖版本，并支持可复现构建（reproducible builds）。

为什么需要 Go Modules？

在 Modules 出现前，Go 依赖管理主要靠：

  • GOPATH 模式：所有代码必须放在 $ GOPATH/src 下
  • vendor 目录：手动复制依赖，但版本混乱、难以维护

这些问题导致：

  • 项目无法放在任意目录
  • 多个项目依赖同一库的不同版本时冲突
  • 构建结果不可复现（今天能跑，明天可能因依赖更新而失败）

Go Modules 的目标：
✅ 项目可放在任意位置
✅ 精确锁定依赖版本
✅ 支持语义化版本（SemVer）
✅ 自动下载、验证、缓存依赖

概念 说明
Module（模块） 一个包含 go.mod 文件的 Go 项目，是依赖管理的基本单位
Module Path（模块路径） 模块的全局唯一标识符，通常为 URL 形式（如 github.com/user/repo）
go.mod 模块的“身份证”，声明模块名、Go 版本、直接依赖
go.sum 依赖的“校验和清单”，确保下载内容未被篡改
Main Module 当前工作目录所在的模块（你正在开发的项目）
Indirect Dependency 被依赖的依赖（A → B → C，则 C 对 A 是 indirect）

常用命令：

命令 作用
go mod init <module-path> 初始化新模块（生成 go.mod）
go get <package> 添加或升级依赖（自动更新 go.mod）
go get <package>@v1.2.3 指定版本安装
go mod tidy 清理未使用的依赖，添加缺失的依赖
go list -m all 列出所有依赖（包括间接依赖）
go mod download 预下载所有依赖到本地缓存
go mod verify 验证依赖是否与 go.sum 一致

四、语法

4.1 包Package 和 Import

什么是 Package？

  • Package 是 Go 代码的基本组织单位。
  • 一个包 = 一个目录 + 若干 .go 文件。
  • 所有 .go 文件必须以 package 包名 开头。
  • 包名通常小写，且与目录名一致（推荐）。
类型 特点
main 包 必须包含 func main()，可编译为可执行程序
普通包（库包） 提供可复用功能，不能直接运行

💡 一个项目只能有一个 main 包作为入口。

Import：引入其他包

使用 import 引入其他包的公开（exported）功能：

  • 调用方式：包名.函数名()，如 fmt.Println()
  • 调用其他包的函数、变量或类型时，必须写上包名作为前缀，不能像某些语言那样“直接使用名字”。（Go 没有“静态导入”或通配符）

可见性控制：靠首字母大小写！

Go 没有 public/private/protected 关键字，而是通过标识符首字母决定是否对外可见：

首字母 可见性 示例
大写（A-Z） 公开（exported），其他包可访问 func Add()、type User
小写（a-z） 私有（unexported），仅本包内可用 func add()、var debug = true

与 Java 的简单对比

特性 Go Java
代码组织单位 Package（目录） Package+类
可见性控制 首字母大小写 public / private / protected 等关键字
导入语法 import "path" import com.example.Class;
命名空间 包名自动作为前缀（fmt.Println） 类名直接使用（需 import）
默认可见性 小写 = 包内私有 无关键字 = 同包可见（package-private）
  • Go 的包更轻量，没有“类”的概念，一切围绕函数和类型组织
  • 推荐用 gofmt 自动格式化 import 分组（标准库在上，第三方在下）

gofmt 是 Go 官方代码格式化工具，能自动统一代码风格（如缩进、空格、import 排序等）。常用命令：gofmt -w file.go 直接修改文件，gofmt -w . 格式化整个项目。它强制规范代码，提升可读性，是 Go 开发的标配工具。

4.2 变量

变量声明与初始化

  • 完整声明：var name string = "Alice"
  • 类型推导：var age = 25（编译器自动推断类型）
  • 短变量声明（仅函数内）：score := 90

✅ 推荐使用 := 简化函数内变量声明。

零值机制

未显式初始化的变量会自动赋予零值，避免未定义行为：

  • int → 0，bool → false，string → ""
  • 指针、切片等 → nil

指针变量

Go语言之所以引入指针类型，主要基于两点考虑，一个是为程序员提供操作变量对应内存数据结构的能力；另一个是为了提高程序的性能（可以极大节省内存空间，操作效率也更高）。

指针在Go语言中有两个使用场景：类型指针和数组切片。

作为类型指针时，允许对这个指针类型的数据进行修改指向其它内存地址，传递数据时如果使用指针则无须拷贝数据从而节省内存空间，此外和C语言中的指针不同，Go语言中的类型指针不能进行偏移和运算，因此更为安全。

  • &x：取地址（得到 *T 类型）
  • *p：解引用（访问指针指向的值）

⚠️ Go 指针不能运算（如 p++ 非法），更安全。

变量类型

  • Go 是静态类型语言，变量类型在编译时确定。
  • 支持基本类型（int, string, bool）、复合类型（数组、切片、map、结构体）等。
  • 类型写在变量名之后：var x int

与 Java 的主要区别

特性 Go Java
声明语法 var x int 或 x := 1 int x = 1;
类型位置 变量名后 变量名前
局部变量初始化 自动零值，可直接用 必须显式初始化，否则编译报错
指针 有，但无指针运算 无（对象引用不是指针）
匿名变量 ✅ _ 丢弃值 ❌ 无

💡 Go 更强调显式、安全、简洁，变量设计服务于并发和系统编程需求。

make vs new

nil 是什么？

  • nil 是指针、切片、map、channel、函数、接口等类型的零值
  • 表示“未初始化”或“空”
  • 不能用于基本类型（如 int, string 不能为 nil）

Go 有“根对象”吗？

**没有！**在Java里面，如果不用多态，没有接口，父类，超类的话，就用Object作为根对象，在Go里面，如果函数参数不知道用什么类型，通常会用 interface{}，这是个空接口，表示任意类型，因为不是弱类型语言，没有any类型，也不是强面向对象语言，没有Object，所以就有这个空接口的出现。

  • Go 不是面向对象语言，没有像 Java 的 Object 这样的“所有类型的基类”

  • 所有类型彼此独立

  • 若需要通用类型，可使用 空接口 interface{}

    （Go 1.18+ 推荐用 any）

💡 这体现了 Go 的设计哲学：组合优于继承，简单优于统一，代码简洁、安全、易于并发

4.3 语法

Go 的流程控制语句设计非常简洁：只有 if、switch、for 三种基本结构，没有 while、do-while 或三元运算符。语法去掉了括号，强调可读性。

条件语句：if / else

  • 条件不用括号 ()（Java 需要）

  • 必须用花括号 {}（即使只有一行）

  • 支持在 if 前加初始化语句（作用域仅限该 if）

🔍 vs Java：

  • Java：if (score >= 60) { ... }（必须括号）
  • Go：if score >= 60 { ... }（无括号，更简洁）
  • Go 没有三元运算符（如 a ? b : c），强制用 if-else 提高可读性

分支语句：switch

  • 自动 break，不会“穿透”到下一个 case（Java 默认会穿透，需手动写 break）

  • 可省略表达式，实现多条件判断：

🔍 vs Java：

  • Java 的 switch 容易因忘记 break 导致 bug
  • Go 的 switch 更安全、更常用（甚至替代复杂 if-else 链）

循环语句：for（Go 只有这一种循环！）

(1) 经典三段式（类似 Java 的 for）

(2) 条件循环（替代 Java 的 while）

(3) 无限循环（替代 while(true)）

(4) 遍历集合：for range

🔍 vs Java：

  • Go 用 for range 替代 Java 的 for-each（for (String f : fruits)）
  • Go 没有 while 关键字，但用 for condition 实现相同效果

AI原生开发，从Claude Code到OpenSpec

最终目的：OpenSpec和spec-kit来开发真实需求。

一、什么是AI原生开发

AI原生开发是什么：AI原生开发工作流可以拆成三根支柱：可执行的规范（Specs）、持久化的上下文、可编排的行动。

1.1 可执行的规范（Specs）【输入，定义做什么】

过去我们习惯把”需求文档”和”代码”当成两回事——文档写给人看，代码才是机器跑的东西。但在AI原生的玩法里，一份好的需求规格说明（Specification，简称Spec），比如spec.md，它本身就应该是一份**”意图代码”**。这就是说这份文档不再是给产品经理或开发者看的那种松散的自然语言描述，而是一份结构化的、AI能精确理解并照着执行的”高级语言”。

它意味着维护软件的重心，从维护那些天天在变的代码，转移到了维护相对稳定的规范上。需求变了，我们先改spec.md，然后让AI重新生成代码。这就是**规范驱动开发（Spec-Driven Development, SDD）**的核心思想。

1.2 持久化的上下文Context【背景，帮助AI理解怎么做】

这就是CLAUDE.md、AGENTS.md这类上下文文件的作用——它们给AI提供了关于项目的”长期记忆”。更妙的是，这种记忆可以分层设计：

企业级记忆：公司层面的安全红线、合规要求，谁都不能违反

项目级记忆：constitution.md里定义的技术选型、架构原则、编码规范

模块级记忆：某个特定模块的API设计、核心业务逻辑

个人级记忆：你自己的代码风格偏好

这种分层设计让AI在不同场景下能拿到合适的背景知识，既保证了一致性，又足够灵活。

1.3 可编排的行动Actions【执行，负责完成它】

AI能干的不只是读文件、写代码。通过自定义指令（Slash Commands）、钩子（Hooks）和MCP服务器，我们可以给它装上各种”外挂”，让它的能力边界几乎无限扩展。

二、AI编程的演进

2.1 AI作为外部知识库，作为一个外部顾问，需要离开开发环境去咨询，例如ChatGPT、Gemini、Claude等，核心价值是信息检索和知识问答。

2.2 AI作为嵌入式副驾驶，包括各类AI插件（如GitHub Copilot Chat），以及像Cursor这样从头开始就围绕AI构建的”AI原生IDE”。这个阶段提供了强大的编码增强能力，但它本质上仍未脱离”辅助开发者”的范畴。AI在这里是一个聪明的助手，但仍然被动、文件级、行动空间受限且环境绑定。

2.3 AI作为原生工作流智能体，以Claude Code为首的命令行AI智能体代表了这一阶段。这类工具可以感知全局、规划行动、与环境交互。它们不再是被动的助手，而是能够主动执行复杂任务的数字”外包”。这正是AI原生开发真正想要达到的状态。

2.4 AI作为自主软件工程师，面向未来，还未实现，比如Claude Code的”Headless模式”（即无需人工授权的”YOLO模式”）。

演进带来的开发者价值的金字塔的倒转：传统开发模式下，顶层是沟通和需求理解，中间层进行设计和架构，底层基石是编码和实现。AI原生开发模式下，底层基石变为意图定义与规范设计，AI完成从清晰指令到代码，开发者需要定义清晰指令。中间层是设计和工作流编排，不光要设计软件架构，还要设计人和AI怎么配合干活。顶层是编码和实现，大量被AI接管。总之，开发者从代码的生产者变为规范设计者，从任务执行者变为AI工作流的指挥家。

三、SDD的本质，代码为王到规范为王

3.1 之前软件开发的难题：意图和实现之间的鸿沟，PRD产品需求文档到设计文档到代码，文档只是参考，代码才是真相。

3.2 SDD的核心主张：让规范成为真相，让代码变为规范的衍生物。就像源代码编译为二进制文件一样，规范编译为代码。前提是规范必须足够精确，精确到AI能直接照着执行。

3.3 AI扮演的角色：智能编译器，接收人类给出的高层级、非结构化的意图描述Spec，一步步把它转化、细化，最终输出可执行的代码。

3.4 SDD的四个阶段：

第一步：意图定义，只关心业务层面的事情，不关心任何技术细节，包括用什么框架，数据怎么存，接口怎么设计。产出一份清晰的意图描述spec.md。

第二步：技术规划，AI拿到意图定义结合项目的技术栈和架构原则，生成技术实现方案，产出架构设计、数据模型、接口规范等。

第三步：任务分解，把技术方案拆成一个个具体的原子级的开发任务，理清任务之间的依赖关系和可并行点。

第四步：自动化实现，建文件、写代码、跑测试。

总结：传统开发围着代码转，SDD围着规范转，但是，现阶段AI在长链路推理上不够稳定，会失忆、会跑偏。

六、关于SDD思考

6.1 SDD的实践层次：

Spec-first（规范先行）：先写规范，再辅助开发（当前主流状态）

Spec-anchored（规范锚定）：规范持续留存，指导后续演进与维护（较少实现）

Spec-as-source（规范即源码）：规范是唯一权威源文件，代码完全由其生成，人类永不直接修改代码（理想但尚未成熟）

6.2 关于SDD的质疑：1、普适性困境：标准化工作流（如spec-kit）难以适配所有问题规模；2、审查成本：大量生成Markdown规范文件，审查难度超过审查代码；3、控制幻觉：AI的上下文理解偏差和推理不稳定而偏离指令；4、规范边界模糊：功能规范和技术规范在实践中何时该抽象何时该具体的失焦。

6.3 SDD和MDD模型驱动开发：都是以高层抽象（UML/自然语言Spec）作为真理之源生成代码，但是LLM无需构建复杂解析器，但是引入非确定性。

6.4 怎么实践：构建项目专属的AI资产，Agent.md、CLAUDE.md、constitution.md；渐进式采用SDD工作流；AI原生开发不是简单的用AI写代码，而是开发范式的根本转变，代码和规范哪个才是真理之源，核心价值是编写代码还是定义意图。

Go 语言简介

Go（又称 Golang）是由 Google 于 2009 年推出的开源编程语言，由 Robert Griesemer、Rob Pike 和 Ken Thompson 设计。其设计目标是简洁、高效、并发友好、易于部署。Go 语法接近 C 语言，但去除了复杂的特性（如继承、泛型早期版本缺失等），内置垃圾回收（GC）、并发原语（goroutine 和 channel），编译速度快，生成静态链接的二进制文件，非常适合构建高性能、高并发的网络服务和云原生应用。

Go 与 Java 的主要区别

维度 Go Java
语言范式 过程式为主，支持简单面向对象（无类、无继承） 纯面向对象（一切皆对象，支持继承、多态）
并发模型 基于 CSP 模型，使用 goroutine + channel，轻量高效 基于线程 + 锁（如 synchronized、ReentrantLock），重量级
运行方式 编译为本地机器码，直接运行二进制 编译为字节码，在 JVM 上运行
内存管理 自动 GC，但更注重低延迟（STW 极短） 自动 GC，JVM 提供多种 GC 算法（如 G1、ZGC）
部署 单一静态二进制文件，无需依赖环境 需安装 JRE/JDK，依赖 classpath 和 jar 包
错误处理 显式返回 error 值，强调“错误是值” 使用 try-catch 异常机制
泛型支持 Go 1.18（2022）起支持泛型 Java 5（2004）起支持泛型
构建速度 极快，适合大型项目快速迭代 相对较慢，尤其大型项目编译耗时
生态与场景 云原生、微服务、CLI 工具、基础设施（如 Docker、K8s） 企业级应用、Android 开发、大数据、传统后端系统

总结

  • Go 更适合：追求开发效率、部署简单、高并发、低延迟的现代云服务。
  • Java 更适合：复杂业务逻辑、强类型安全、成熟企业生态、长期维护的大型系统。

两者并非替代关系，而是适用于不同场景。许多公司甚至在架构中同时使用 Go（做网关/中间件）和 Java（做核心业务）。

Go 是编译型语言。

具体来说，Go 源代码（.go 文件）通过 Go 编译器（如 go build）被直接编译成目标平台的机器码，生成一个独立的、静态链接的可执行二进制文件。这个文件不依赖 Go 运行时环境或虚拟机，可以直接在相同操作系统和架构的机器上运行。

这与解释型语言（如 Python、JavaScript）不同——后者通常需要解释器逐行读取并执行源代码；也不同于 Java 这类“半编译”语言（编译为字节码，再由 JVM 解释或 JIT 编译执行）。

✅ Go 的编译特点包括：

  • 编译速度快；
  • 生成单一可执行文件，部署简单；

1. Go 的协程（Goroutine）是什么？
Goroutine 是 Go 语言提供的轻量级并发执行单元，由 Go 运行时调度，而非操作系统线程。启动成本低（初始栈仅 2KB），可同时运行成千上万个，通过 channel 安全通信，是 Go 高并发模型的核心。

2. defer 的作用和执行顺序？
defer 用于延迟执行函数调用，常用于资源释放（如关闭文件）。多个 defer 按“后进先出”（LIFO）顺序执行，在函数 return 前、panic 后仍会执行，确保清理逻辑可靠。

3. Go 中如何实现面向接口编程？
Go 采用隐式接口实现：只要类型实现了接口的所有方法，就自动满足该接口，无需显式声明（如 Java 的 implements）。这提高了代码灵活性，便于解耦和测试。

4. slice 和 array 有什么区别？
Array 是固定长度的值类型，赋值会复制全部元素；slice 是动态长度的引用类型，包含指向底层数组的指针、长度和容量。slice 更常用，支持 append 等操作。

5. map 是线程安全的吗？如何安全使用？
map 不是并发安全的，多个 Goroutine 同时读写会导致 panic。应使用 sync.RWMutex 保护，或在读多写少场景下使用 sync.Map，避免数据竞争。

6. channel 的用途和注意事项？
channel 用于 Goroutine 间通信和同步。nil channel 读写会永久阻塞；向已关闭 channel 发送数据会 panic；应由发送方关闭 channel，接收方可通过 ok-idiom 判断是否关闭。

7. Go 的内存逃逸是什么？如何查看？
当局部变量在函数返回后仍被引用，编译器会将其分配到堆上（逃逸）。可通过 go build -gcflags="-m" 查看逃逸分析结果，有助于优化性能和减少 GC 压力。

8. context 包的作用是什么？
context 用于传递请求生命周期内的取消信号、超时和上下文数据。常用于 HTTP 服务、数据库调用等，实现跨 Goroutine 的优雅取消与超时控制，避免资源泄漏。

9. Go 中如何处理错误？
Go 采用显式错误返回机制，函数通常返回 (value, error)。调用者必须显式检查 error，不依赖异常。panic/recover 仅用于不可恢复的严重错误，不用于常规流程控制。

10. init 函数的执行时机和用途？
init 函数在包被导入时自动执行，早于 main 函数。用于初始化全局变量、注册驱动或设置配置。同一包内多个 init 按文件名和定义顺序执行，每个文件可有多个 init。

11. Go 的垃圾回收（GC）机制是怎样的？
Go 使用并发、三色标记清除算法的 GC，从 1.5 版本起实现低延迟（STW 时间通常 < 100 微秒）。GC 自动管理堆内存，开发者无需手动释放。可通过 GOGC 环境变量调整触发频率。

12. 什么是 sync.WaitGroup？如何使用？
sync.WaitGroup 用于等待一组 Goroutine 执行完毕。主 Goroutine 调用 Add(n) 增加计数，每个子 Goroutine 完成后调用 Done()，主 Goroutine 通过 Wait() 阻塞直到计数归零。

13. Go 中的 nil 是什么？哪些类型可以为 nil？
nil 是 Go 中指针、切片、map、channel、函数、接口等类型的零值，表示“未初始化”或“空”。注意：数组、结构体、基本类型（如 int、bool）不能为 nil。

14. make 和 new 的区别是什么？
new(T) 分配类型 T 的零值内存并返回 *T；make 仅用于 slice、map、channel，不仅分配内存还完成初始化（如设置长度、容量），返回的是 T 而非指针。

15. Go 中如何避免 Goroutine 泄漏？
Goroutine 泄漏常因未正确退出导致。应使用 context 控制生命周期、确保 channel 通信有接收方、避免无限循环无退出条件。监控工具（如 pprof）可辅助检测。

16. 说说 Go 的调度模型（GMP 模型）？
Go 采用 GMP 调度模型：G（Goroutine）、M（系统线程）、P（逻辑处理器）。P 维护本地 Goroutine 队列，M 绑定 P 执行 G。该模型实现高效并发与负载均衡。

17. 互斥锁（Mutex）和读写锁（RWMutex）的区别？
sync.Mutex 同一时间只允许一个 Goroutine 访问临界区；sync.RWMutex 允许多个读操作并发，但写操作独占。适用于读多写少场景以提升并发性能。

18. Go 中字符串（string）可以修改吗？为什么？
不可以。Go 的 string 是只读的字节序列，底层为不可变数组。若需修改，应转为 []byte 处理后再转回 string，但会引发内存拷贝，需注意性能开销。

19. 什么是空 struct{}？有什么用途？
struct{} 是零大小的结构体，不占用内存。常用于 channel 通信中仅传递信号（如 chan struct{}），或作为 map 的值实现集合（set）功能，节省内存。

20. Go 支持泛型吗？如何使用？
从 Go 1.18 起支持泛型。通过类型参数（如 func Print[T any](v T)）编写通用函数或类型。泛型提升代码复用性，同时保持编译时类型安全，避免 interface{} 的类型断言开销。

2、文本分类

背景：文本分类在网页检索、信息检索等领域很重要，传统基于神经网络的模型虽然性能好，但是在训练和测试时非常慢，限制在大规模数据集上的使用。同时，线性分类器通常被认为是文本分类问题的强基线。

本文展示了具有秩约束和快速损失近似的线性模型，可以在10分钟内训练10亿个单词，同时实现与最先进的性能相当的性能。

模型架构：本质上是一个**“词向量平均 + 线性分类器”**的浅层网络。具体做法是：先用矩阵 A 将输入文本的词或 n‑gram 映射为低维向量，再对这些向量求平均得到句子/文档表示；然后用矩阵 B 将该表示映射到类别空间，并通过 softmax（大类别数时用分层 softmax）输出类别概率。整个模型可视作带低秩约束的线性分类器，结构简单、训练极快。FastText不使用预训练的词嵌入。

使用霍夫曼树作为输出层（即Hierarcial Softmax），非叶子节点上的向量为二分类提供计算，叶子节点对应的是所有类别（而不是词汇表所有词的向量）。
模型开始训练时，词向量（参数）随机初始化，结束后保存起来用于预测就行，目的是分类，而不是词向量。
Fasttext模型的输入不仅仅是针对每个单词，并且加入了词序信息，词序信息通过n-gram的形式加入。n-gram对应的单位是word，而不是char。

Fasttext工具包的优势：
在保持较高精度的情况下, 快速的进行训练和预测是fasttext的最大优势。
FastText 是开源的，用户可以自由使用、修改和分发。
Fasttext工具包中内含的Fasttext模型具有十分简单的网络结构。

由于fasttext模型过于简单，无法捕捉词序特征，因此会进行n-gram特征提取以弥补模型缺陷提升精度。

使用fasttext模型训练词向量时使用层次softmax结构，来提升超多类别下的模型性能。

可进行的文本分类任务：二分类、单标签多分类、多标签多分类。

Fasttext训练： FastText 的训练数据需要满足以下格式：每行样本的格式为：__label__<标签> <文本>

3、词向量表示

Fasttext是继word2vec词向量模型提出之后提出的模型（或者说算法），因为训练速度非常快而比较受工业界关注。

FastText 的词向量表示原理基于子词（subword）机制：它将每个词拆解为字符级 n-gram（如 tri-gram）并添加边界符号，同时保留原词本身作为一个单元；该词的最终向量表示是其所有子词（包括原词）对应向量的平均值。这种设计使得即使遇到训练中未出现的词（OOV），只要其子词在其他词中出现过，也能通过子词向量组合生成合理的语义表示，从而有效处理罕见词、拼写变体和形态丰富的语言。

使用负采样的skip-gram，将每个中心词看作子词的集合，并学习这些子词的词向量。

子词(subword)是论文核心，以中心词为where为例，设定子词大小为3，那么子词集合分为两部分，整词和子词。
整词即<where>
子词<wh, whe, her,ere,re>
最终<wh, whe, her,ere,re, where>
背景词则直接使用整词。 输入层使用子词+整词，输出层使用整词。 如果OOV，则使用子词的向量和表示该词，这也是subword的一个优势所在。

4、FastText模型训练参数

FastText模型训练支持多种参数，这些参数允许用户根据具体任务需求对模型进行细致的定制。

词向量的维度： 词向量的维度并没有一个固定的标准，它可以根据具体的应用场景和模型需求来设定。
50维：资源受限或轻量级应用（如移动端），牺牲部分语义精度换取低内存和快速推理。
100维：通用型选择，适用于多数文本分类、检索等中等复杂度任务。
300维：主流预训练模型（Word2Vec、GloVe、FastText）默认配置，在语义丰富性和性能间取得良好平衡。
大于300维（如500+）：用于高精度需求的复杂任务（如机器翻译、语义解析），但显著增加计算与存储开销。

维度过大：内存与计算成本剧增、小数据下易过拟合、优化困难，收敛慢。
维度过小： 语义信息表达不足、难以区分近义/反义词、模型表示与泛化能力受限。
实践建议：起点推荐：从 100–300 维 开始实验；调参策略：结合任务复杂度、数据规模和硬件条件，通过验证集性能对比不同维度。

Epoch参数： Epoch（训练周期）：模型完整遍历一遍训练集并更新参数一次。

Iteration（迭代）：一次用一个 batch 做前向 + 反向 + 参数更新叫一次迭代。若数据集被切成 n 个 batch，则：1 个 Epoch = n 次 Iteration。

Epoch 过少（训练不够）：容易欠拟合、性能不稳定：结果高度依赖初始化，多次训练差异可能较大。
Epoch 过多（训练过头）：容易过拟合、浪费资源：后期收益很小，却消耗大量时间和算力。有时会在局部最优或鞍点附近“打转”，增加 Epoch 也不再提升效果。

如何选择合适的 Epoch 数：
早停法（Early Stopping）：监控验证集效果，不再提升甚至下降时停止训练。
学习率调整：配合学习率衰减，在多 Epoch 的训练中前期快学、后期细调。
交叉验证：在不同数据划分上评估，帮助确定合理的 Epoch 数。
实践中，常见的Epoch数范围可以从几十到几百不等，具体取决于数据集大小、模型复杂度以及任务的难易程度。

ngram参数：在FastText模型中，n-grams（也称为字符n-grams）是一个关键参数，用于捕获词内部的字符级组合信息。n-gram的大小（n值）对模型性能有着重要影响。

n-grams 太小的影响（如 n=1,2）
信息不足：只能看到单字符或短组合，难以捕捉词内部较复杂的形态和语义结构。
区分能力弱：对形近词、细微语义差别的词，表示能力有限，影响模型在分类、序列标注等任务上的泛化。

n-grams 太大的影响
维度 / 特征数暴涨：n 增大后 n-gram 组合数激增，导致模型维度高、内存和计算成本显著上升。
特征稀疏：很多长 n-gram 在语料中极少出现，信息利用率低，噪声多、信号少。
过拟合风险增大：高维稀疏特征容易让模型记住训练数据中的偶然模式和噪声，泛化变差。

如何选择合适的 n-grams：
需要在 信息丰富度 和 计算/稀疏性/过拟合风险 之间折中。
使用较小的 n，如 2～3，既能捕获一定的内部结构，又避免维度爆炸。
针对具体任务和数据，通过在验证集上对不同 n 值（或 n 范围，如 3–6）做实验，选择效果最好的设置。
可以组合多个 n 值（例如同时用 3、4、5-gram）以提升表现，但要配合合理的哈希桶数和资源限制。

5、分层softmax

例如有一个文本分类任务，包含四个类别：A、B、C、D。对应不同频率，首先根据类别的频率构建哈夫曼树。

1、初始化：将每个类别作为一个叶节点，并赋予其频率。
2、合并：每次选择两个频率最小的节点，合并成一个新的内部节点，新节点的频率是这两个节点频率之和。
3、重复：重复上述步骤，直到所有节点都被合并成一个根节点。

这样，每个类别的路径可以表示为从根节点到叶子结点的一系列二进制决策（左子树还是右子树）。分层Softmax减少了计算复杂度，特别在处理大量类别的分类任务时，每个节点是一个二分类器，提高训练效率和内存使用效率。

6、pytorch重构fasttext

背景：大语言模型预训练数据：多样广泛、高质量、规模庞大。对网页内容进行分类时，通常使用fasttext、bert模型，性能要求高、精确程度要求高。分类模型流程：分词、token化、向量化、推理得到结果。

为提高性能进行批处理：批处理将一批数据以一个矩阵的形式表达，通过多次矩阵计算来计算结果，避免显式的for循环。使用np.dot进行可以得到两个数量级的优化。但是fasttext的列表预测接口并未使用批处理，仍然使用的for循环。因此可以重构fasttext，或从fasttext导出权重，进行手动矩阵计算。

6.1、导出权重：fasttext支持将权重参数导出。

提取输出矩阵，如果加载的是 词向量模型（如 cc.en.300.bin），get_output_matrix() 返回的是 Skip-gram 的输出向量（用于预测上下文），不能直接用于分类。如果加载的是 文本分类模型（通过 fasttext supervised 训练），则 get_output_matrix() 才是真正的 分类权重矩阵（每行对应一个类别）。

问题：召回率低，算法相对保守。应该增加掩盖masked操作和调整最大序列长度。

矩阵运算需要长度补齐，由于引入了batch，所以在将所有的词进行均值计算的时候，也需要将补齐的元素进行掩盖，防止补齐的token被引入到计算。

最大序列长度max_length是控制每个序列（文本）的长度，所有的输入文本都会被截断/补齐到这个长度，以进行批处理。但是训练阶段的max_length已经确定，无法对其内部的截断/补齐的逻辑进行修改。

6.2、pytorch重构fasttext

把训练阶段的max_length与推理阶段的max_length进行对齐，召回率随着max_length的提升，逐步升级到了70%左右。

反映一个模型的训练效果，最直接的方式就观察其训练阶段的损失值的曲线，横坐标是训练步数，纵坐标是损失值，损失曲线应该是逐步下降的，光滑完整的。曲线有较多尖刺和凸起，意味着损失值上下起伏，模型学习能力反复。有以下几种解释：
1、学习率过高：当学习率设置过高时，模型在每次更新时可能会跳过最优解附近的区域，导致损失在不同的迭代间波动较大。
2、数据噪声：如果训练数据中存在较多的噪声，模型可能难以很好地拟合数据，从而导致损失值出现波动。
3、模型容量：模型可能过于简单（对于fasttext，该模型确实不复杂），无法有效捕捉数据的复杂模式，或过于复杂，导致在训练数据上过拟合。
4、批量大小：使用较小的批量大小可能会导致损失曲线更为震荡，因为每次迭代中的梯度估计可能会有较大变化。

针对学习率过高：使用学习率Scheduler，一种用于动态调整神经网络训练过程中学习率的机制。可以固定步长衰减，每隔一定的训练步数（或epoch）将学习率降低一个固定比例。可以指数衰减，可以余弦退火。在PyTorch中，可以使用torch.optim.lr_scheduler模块来方便地设置这些策略。scheduler = torch.optim.lr_scheduler.StepLR(optimizer, step_size=1, gamma=0.9)

针对批量大小：小批量梯度下降（在每次参数更新时使用训练集中的一小部分数据mini-batch，例如32、64或128个样本。过小可能造成收敛过程不稳定）与批量梯度下降（在每次参数更新时使用整个训练集的所有数据）。调整batch_size，越大损失值的震荡情况越小。

最常见的防止过拟合的手段就是dropout，设置丢弃概率，训练时一定概率的神经元被丢弃。

Transformers 提供了一些快速高效的分词包，主要用于自然语言处理任务。如BertTokenizerFast、RobertaTokenizerFast、GPT2TokenizerFast。

注意训练和推理时使用的分词器应该一致，因为在不同场景(代码，数学等)下，会有不同的算法提供不同的fasttext模型（bin文件），bin文件推理做两个步骤：分词和推理。pytorch生成的模型是一个.pth文件，入参是一个张量，而不是字符串，从字符串到张量，需要分词、token化、向量化。分词方式有ngram分词方式、transformers加载分词文件的分词方式。

批量运算，使用masked，将输入变为矩阵，需要进行pad/truncated(补充或者截断)。使用 transformers 库可以方便地进行 pad/truncated。注意padding参数，true表示补齐到batch的最长的样本序列长度，max_length表示所有数据补齐到该值，设置2048.

对于一个具体的工作项目，从制定规划起一直到更新为止，全部过程可分为七个阶段：

1.规划阶段。即调研、程序设计阶段，目的在于谋求活动的规划与战略；

2.拟定方案。提出具体的计划方案。

3.研制阶段。作出研制方案及生产计划。

4.生产阶段。生产出系统的零部件及整个系统，并提出安装计划。

5.安装阶段。将系统安装完毕，并完成系统的运行计划。

6.运行阶段。系统按照预期的用途开展服务。

7.更新阶段。即为了提高系统功能，取消旧系统而代之以新系统，或改进原有系统，使之更加有效地工作。

MinHash与MinHashLSH

MinHash 是一种用于快速估计两个集合（如文档、网页等）之间相似度的算法，特别是在处理高维数据或海量数据时非常高效。主要用于计算 Jaccard 相似度（集合交集与并集的比值）。Jaccard 相似度需要遍历整个集合，耗费时间和内存。

MinHash 提供了一种近似计算的方法，通过构造 “简化签名” 来高效估算集合之间的相似性，而无需直接操作整个集合。

计算步骤：输入分词集合，定义n个哈希函数，集合中每个元素使用哈希函数计算，得到对应最小值，生成n大小的签名矩阵，比较签名中相同值的占比，得到近似的Jaccard相似度。 特点：minhash签名固定大小，降低计算复杂度；近似方法允许误差；适用于大规模文档去重、相似性查找等。

MinhashLSH：局部敏感哈希，在MinHash的基础上进一步优化，通过分桶的方式将高相似度的数据快速归类到相同的桶中，减少不必要的相似性计算。

实战操作：首先将文本使用集合或者向量来表示，将文本进行分词，但是单纯分词变为集合没有考虑词间顺序问题，所以分词之后再用ngram来考虑顺序。然后使用jaccard系数表示两个集合的相似性，交集/并集。 这样有两个问题：文本数量非常大、文本本身篇幅非常长。所以有两个优化方向：减少集合的长度、减少计算相似度的次数。

使用minhash：根据分词组成的集合产生经过某种处理后的一组哈希值，相近的文本生成的哈希值相似度比较高。常用两种方法生成哈希值：1）使用一个哈希函数进行哈希后再进行多次重排。2）使用不同的哈希函数进行多次哈希。

1）使用一个哈希函数进行哈希后再进行多次重排：用一个基础哈希函数对集合中元素求hash，然后使用多个简单的数学变换模拟重排，然后每次排列中取最小值作为每次打乱的代表。n次排列生成n序列哈希值。

2）使用不同的哈希函数进行多次哈希（常用）：选取一批相互独立的哈希函数，每个函数对集合中元素求hash，选取该次哈希变换后集合中数值的最小值。不同的哈希函数相当于不同的投影规则。n个哈希函数生成n序列哈希值。

minhash解决了文本向量表示维度的问题，但是两两比较次数太多的问题还在。如果能识别出相近的和不相近的，可以大大减少计算量。做法：借助局部敏感哈希( (Locality Sensitive Hashing，LSH) 来先进行一次分组或者聚类，让相近的文本分到一组去。

Transform 的架构，Encoder 和 Decoder

Transformer架构是一种用于序列数据处理的深度学习模型，特别适用于自然语言处理任务。它摒弃了传统的循环神经网络（RNN）和卷积神经网络（CNN），完全基于注意力机制（Attention Mechanism）构建。

Encoder（编码器）：由多个相同的层堆叠而成，每层包括一个多头自注意力机制（Multi-Head Self-Attention）和一个位置前馈神经网络（Position-wise Feed-Forward Network）。编码器负责将输入序列转换为隐藏表示，这些表示捕捉了序列中元素之间的依赖关系，并且每个位置的信息都能被传递到下一个层次。

Decoder（解码器）：同样由多个相同层组成，除了包含与编码器类似的组件外，还增加了一个额外的多头注意力层，称为“编码器-解码器注意力”层。这个层允许解码器关注到编码器的所有输出，帮助生成目标序列。此外，解码器在每个时间步只能访问到当前及之前的时间步信息，以保证预测的正确顺序。

通过这种结构，Transformer能够高效地并行训练，并显著提升处理长距离依赖问题的能力。

MCP

MCP 是什么： Model Context Protocol，Anthropic (Claude) 主导发布的一个标准协议。让 AI 模型能够与不同的数据源和工具进行无缝交互。它就像 USB-C 接口一样统一标准。

MCP 架构：客户端 - 服务器架构，包含：MCP 主机（MCP Hosts）：发起请求的 AI 应用程序，比如聊天机器人、AI 驱动的 IDE 等。MCP 客户端（MCP Clients）：在主机程序内部，作为Host的中介，管理 MCP Host与一个或多个 MCP 服务器之间的通信。MCP 服务器（MCP Servers）：为 MCP 客户端提供上下文、工具和提示信息。本地资源（Local Resources）：本地计算机中可供 MCP 服务器安全访问的资源，如文件、数据库。远程资源（Remote Resources）：MCP 服务器可以连接到的远程资源，如通过 API 提供的数据。

MCP 优点：统一标准不用重复造轮子、数据不用上传到云端，AI 直接在本地处理。

MCP的诞生标志着prompt engineering进入了一个新的发展阶段，它通过提供更结构化的上下文信息，显著提升了模型的能力。没有MCP时，需要手动从数据库中筛选信息或使用工具来检索相关信息，OpenAI引入function call，允许模型根据需要调用预定义函数以获取数据或执行特定操作，但是对平台高度依赖，不同LLM平台间API实现存在差异，切换模型时需要重写代码。MCP提供丰富的插件库，不限于特定的AI模型。

MCP如何调用工具：MCP的选择机制基于prompt实现。客户端将问题发送给LLM，LLM分析可用工具并选择，客户端通过MCP Server执行所选的工具，工具执行结果返回LLM，LLM结合执行结果，归纳总结回答用户问题。模型是依靠prompt来识别当前可用的工具有哪些。具体做法是，我们将各个工具的使用描述以文本形式传递给模型，从而使模型能够了解有哪些工具可供选择，并基于实时情况做出最佳选择。模型是通过 prompt engineering，即提供所有工具的结构化描述和 few-shot 的 example 来确定该使用哪些工具。

1、理念：通用协议，为大模型与外部的工具和数据源提供统一的通信接口；

2、架构：典型的客户端-服务端架构。

3、信息组织：基于JSON-RPC协议，高度标准化。

4、通信模式：支持交互式、持续性的上下文管理。

既生Function Call，何生MCP：

Function call 的能力来源于大模型的后训练，详细来说，就是给大模型一些选择工具的样本，让模型学会在合适的时机决策需要调用工具。但是不同用户的工具定义格式是不同的，为了把用户的请求和大模型厂商微调的格式对上，所以才有了 function call。Function call 本质是就是每个大模型厂家的事实标准。但是复用性差，解决办法：1.让模型针对具体任务生成个性化代码，只需要额外提供一个代码编译运行环境即可，Manus。2.用一个中间层包装一下，把中间层做成标准，MCP。

  • R1：只用少量高质量的样本数据产生强大的reasoning能力，基于v3，经历四个训练阶段：1、cold-start高质量微调：少量高质量的Cot数据（r1-zero生成）做模型微调，让模型产生出反思、验证的过程。2、第一轮RL，获得reasoning能力，重点在数学、编程、科学等方面的强化学习。3、微调SFT，利用其模型产生一批prompt和response，在各种通识领域，合计800K样本，只微调2epoch。4、第二轮RL，全域强化学习，对数学代码等仍采用简单的rule-based的奖励信号，对其他场景，采用人类对齐的reward model。

  • 蒸馏：以R1为教师，选择qwen2.5的1.5b-32b和llama3的8b和72b，进行SFT微调（蒸馏）。数据准备：671b教师模型生成高质量推理数据样本，作为学生模型的训练样本。数据增强：进一步扩展、修改和优化，多样性和代表性。蒸馏：学习教师模型的输出概率，采用混合损失函数设计（输出概率分布接近教师模型，输出概率分布接近真值）。L2正则化防止过拟合。

  • deepseek-r1-zero：在基础模型DeepSeek-V3上进行强化学习（RL）后得到了DeepSeek-R1-Zero模型。该模型学会了如何推理、创建思维链序列，并具备自我验证和反思等能力。尽管DeepSeek-R1-Zero的学习能力令人惊叹，但它存在语言混合、可读性差等严重问题。

  • deepseek-r1：首先使用数千个思维链（CoT）序列示例形式的冷启动数据，在DeepSeek-V3上进行监督微调（SFT），目的是为强化学习创建一个更稳定的起点，解决DeepSeek-R1-Zero存在的问题。接着进行强化学习，并设置奖励机制，以促进语言一致性，增强在科学、编码和数学等任务上的推理能力。然后，再次进行监督微调，这次加入了非推理重点的训练示例，帮助模型保留写作、角色扮演等更多通用能力。最后，再次进行强化学习，以更好地符合人类偏好。最终得到了一个拥有6710亿参数的高性能模型。（为了加快训练，deepseek加入了SFT的数据解决冷启动的问题，通过R1-Zero生成SFT的数据，解决了R1的冷启动问题。）

  • deepseek-r1-distill：基于Qwen和Llama架构，对参数在15亿 - 700亿之间的较小模型进行微调，得到了一组更轻量、更高效且推理能力更强的模型。这极大地提高了开发人员的可及性，因为许多提炼后的模型可以在他们的设备上快速运行。

  • deepseek的两点贡献：训练成本下降（混合精度、GRPO）、思维链/深度思考增强（纯强化学习、冷启动数据和多阶段训练）。并没有抛弃SFT，在R1训练中加入了大量高质量的数据（结果正确+思维链完整）进行SFT。

  • deepseek在算法创新上，MLA、GRPO。以及强大的实验迭代能力，整个链路（数据、模型结构、训练算法流程、训练架构优化等）众多方案中找到可行的。海量优化空间中找到对的路径。

强化学习

强化学习（Reinforcement Learning, RL）是机器学习的一个重要分支，其核心思想是通过智能体（Agent）与环境（Environment）的交互，学习一种策略（Policy），以最大化长期累积奖励（Reward）。与监督学习和无监督学习不同，强化学习更关注在动态环境中的决策与优化。

  • 核心概念
  1. 智能体（Agent）：学习的主体，负责与环境交互并做出决策。
  2. 环境（Environment）：智能体所处的世界，根据智能体的动作给出反馈。
  3. 状态（State）：环境在某一时刻的描述。
  4. 动作（Action）：智能体在某个状态下可以执行的操作。
  5. 奖励（Reward）：环境对智能体动作的即时反馈（正/负/零），指导学习方向。
  6. 策略（Policy）：智能体的行为规则，即从状态到动作的映射。
  7. 价值函数（Value Function）：评估某个状态或动作的长期价值（未来累积奖励的期望）。
  • 关键特点

- 试错学习（Trial and Error）：通过不断尝试、接收反馈（奖励或惩罚）来优化策略。

- 延迟奖励（Delayed Reward）：当前动作可能影响未来的长期收益，需权衡即时与未来奖励。

- 动态环境：环境可能随时间变化，智能体需适应不确定性。

质量提升Prox

https://blog.csdn.net/python12222_/article/details/142684959

  • Program-Every-Example (ProX) 是上海交大联合研究的一个用于提升大规模预训练语料质量的数据优化框架。
  • 大规模预训练数据是构建强大语言模型的基础。业界的实践通常是抓取互联网上的海量的网页数据，然后人工设计专门的规则来进行数据清洗，这些规则虽然能够在处理上万亿 token 级别的语料时保持较高的效率，但其局限性也逐渐显现。数据的清洗效果往往决于规则是否全面，然而这些规则并不能理解文档中的上下文语境，同时也很难为每一个文档去定制规则，因此面对多样化的样本需求，这些静态规则难以灵活应对，导致语料质量提升空间有限，制约了模型的进一步突破。
  • 上海交大提出Program-Every-Example (ProX) 框架。ProX 通过采用语言模型而非人类规则进行自动化的数据优化，灵活应对多样化的样本特征，显著提升了预训练语料的质量。
  • ProX 不仅可以识别低质量的文本，还能进行更精准的优化和清理，如字符串标准化、噪声行删除等操作，确保每个样本都能以最佳状态进入预训练过程。总体框架：利用语言模型生成程序 + 执行，提升数据质量。
  • 文档级别的数据过滤和选择，能够有效识别低质量的文档并加以排除，提升数据集的质量。但是，其精细化处理能力不足，通常只停留在文档的选择层面，可能没有进一步对文档内的细节进行更深入的优化和清理，例如字符级别的规范化处理、噪声行的删除等操作，从而限制了数据优化的效果。
  • 数据合成方法通过大语言模型（LLM）基于种子数据或特定话题，主动生成新的高质量数据。这种合成技术尽管展示了生成多样化、丰富语料的潜力，但其挑战在于需要极大的计算资源支持，特别是在大规模生成时，计算代价非常高。LLM 生成的数据还面临幻觉问题，即生成内容与事实不符，无法保证训练数据的真实性和一致性。
  • Prox：通过使用较小的语言模型（如 0.3B 的超小规模模型）来执行数据优化任务，并且将数据优化的过程转变为调用特定的 python 函数。对每个文档都生成特定的函数调用。ProX 框架会再通过执行这些程序，来对语料进行文档级别的过滤和噪声行、字符级别的处理。做到了简单过滤方法无法实现的精细化操作。ProX 设计的函数接口，覆盖了文档级别过滤、噪声行去除、字符串清洗等操作。
  • 针对数据优化的粒度，ProX 将优化分为两个阶段：文档级别和子文档 / 块级别 (将文档切分成更小的窗口)，分别对应文档级别的过滤和更细粒度的块内优化如行级别和字符级别的优化。ProX 合成了对应的微调数据，以便对基座模型进行微调以处理和优化真实的语料。
  • 在文档级别操作中，借鉴self-rewarding以及fineweb-edu中采用的评分机制，构建出保留高分文档，去除低分文档的优化程序。
  • 在chunk块级别操作中，利用了 Llama-3 和少样本提示的方法，构造了对于多种噪声的函数调用，并对这些离散的函数调用进行语法检查和正确性分析，筛选然后合并为一个较为复杂的程序。

PPL

  • PPL困惑度Perplexity，是衡量语言模型对一段文本“不确定性”的一种量化方式。困惑度越低，说明语言模型对这段文本的预测越“自信”，也就是说文本越符合语言模型学到的语言规律。意味着逻辑清晰，语法通顺。
  • 计算方法：语言模型对整个句子概率的对数，取负数之后exp指数函数。很好预测时，概率高，对数概率接近0，ppl很小。预测不确定时，概率低，对数概率是很大的负数，ppl很大。
    PPL局限性：对长文本不敏感，长文本的 PPL 容易偏高，建议按 token 归一化。不考虑语义，PPL 只反映语言模型是否熟悉该结构，不代表语义正确。模型依赖性强，使用不同语言模型（如 GPT vs BERT）会得到不同的 PPL 值。

ultra-fineweb

  • 模型驱动的数据过滤方法：1、缺乏有效的数据验证策略使得很难及时就数据质量提供反馈。2、用于训练分类器的种子数据的选择缺乏明确的标准，严重依赖人类的专业知识，引入了一定程度的主观性。
  • 要做什么：1、快速评估数据对LLM的影响。2、高效的数据过滤流水线，采用了基于FastText的轻量级分类器。
  • 早期的方法通常依赖于使用手动规则的启发式过滤，这些启发式方法无法识别复杂的内容噪声。 因此，采用神经分类器选择高质量内容的模型数据过滤已成为更好的选择。
  • 传统的方法通过使用候选语料库从头开始训练LLM来验证数据质量。本文提出的有效验证策略利用了几乎训练有素的LLM作为基础，在最后的训练步骤中纳入候选语料库，并将由此产生的性能改进用作评估数据质量的指标。

fasttext

  • fastText是Facebook于2016年开源的一个词向量计算和文本分类工具。在文本分类任务中，fastText（浅层网络）往往能取得和深度网络相媲美的精度，却在训练时间上比深度网络快许多数量级。主要用于生成词向量（word embeddings）和快速进行文本分类。相较于其他工具（如 Word2Vec），FastText 计算速度更快、内存效率更高，非常适合大规模文本处理任务。
  • softmax回归：用于把模型的分数变成概率，归一化到0-1。
